    Counting two machines without opening a port

    Work happens on the laptop and on a Hetzner box. Counting only one is worse than counting neither — it looks precise and is wrong. This is a zero-dependency collector on loopback, a Stop hook that must never fail a turn, and a flat file that gets re-read on every request.

    01 · the shape

    Nothing touches the internet except Tailscale

    The collector binds to 127.0.0.1:8787 and nothing else. That isn't caution for its own sake — the box has no firewall, so binding wider would put /ingest and /stats on the raw internet with a bearer token as the only thing in the way. The source comment names BIND=0.0.0.0 specifically as the failure mode rather than leaving it implied.

    Tailscale Funnel is the entire security model: it terminates HTTPS on a free *.ts.net name and proxies down to loopback, so the Node process never handles TLS, and no inbound port is ever opened.

    Two Claude Code installs write here, running the same hook file with different targets: the cloud host posts to localhost because it is the box, and the Mac goes through the Funnel. Only MINAMI_SOURCE differs.

    Keep it on loopback

    There is no firewall on this box. BIND must stay 127.0.0.1 — the Funnel already reaches it, so a wider bind buys nothing and exposes everything.

    02 · the emitter

    A hook that must never fail a turn

    Every turn on either machine ends with Claude Code firing its Stop hook. The hook reads the last usage block out of the transcript and posts a compact event. Its entire design philosophy is one line of its own docstring: never blocks a turn, fails silent on any error. Missing config? Return. Unparsable stdin? Return. Every failure path is a bare return, never a raise — because a metrics hook that can break your actual work is worse than no metrics.

    It smuggles a second payload along the same event: a session digest — the cwd, the first line of your last message truncated to 60 characters, and the last reply truncated to 100. No model call, pure truncation. Since Stop already fires once per turn, the digest is free, and it's what powers the cross-machine "what are we doing here" feed.

    The POST goes out through curl, not Python's own HTTP client — because urllib can't find the CA bundle on macOS, while curl uses the system cert store. One code path that works identically on both machines beats two that each work on one.

    # the whole philosophy, in the failure paths
try:
    payload = json.load(sys.stdin)
except (json.JSONDecodeError, ValueError):
    return            # not raise — a broken hook must never break the turn

    03 · the crash

    JSON.parse("null") does not throw

    This is the sharpest incident in the codebase, and it's four characters long. null is valid JSON. The original ingest handler wrapped the parse in a try/catch — which is correct, and completely useless here, because parsing "null" succeeds. It returns the value null, sails past the catch, and the very next line does e.ts = e.ts || Date.now() on it.

    That TypeError had nothing to catch it. Unlike the Next app, this standalone script had no process-level handler — so one malformed POST killed the whole collector. Every connected dashboard's stream dropped, and any in-flight event from the other machine was lost with it. One bad client degrades observability for both.

    null.payload
    step 1 / 5

    try { e = JSON.parse(body); } catch { return send(res, 400, { error: "bad json" }); }
// JSON.parse("null") succeeds — the catch above never fires for it, and `e.ts = ...`
// on null throws a TypeError with nothing catching it, killing the whole process.
if (!e || typeof e !== "object") return send(res, 400, { error: "bad json" });
e.ts = e.ts || Date.now();

    The fix is two-layered on purpose. The type guard closes this hole; a process-level uncaughtException handler that logs and exits makes sure the next unknown failure gets a clean systemd restart instead of a zombie process serving stale state.

    04 · the store

    There is no database

    events.jsonl is the entire datastore — one JSON object appended per line. No schema, no index, no migration. Every read endpoint re-reads the whole file and re-derives its answer from scratch. At roughly one line per turn across two machines, that stays cheap for a very long time, and a real time-series database would be more operational surface than the problem justifies.

    Malformed lines are dropped silently rather than failing the aggregate — so a half-written line from a crash mid-append costs you one event, not the whole endpoint.

    /projects takes the same idea further and has no storage at all. It walks the same file and keeps only the most recent event per cwd, which makes it self-pruning by construction: it's always "latest per project", never an accumulating log.

    function readEvents() {
  try {
    return fs.readFileSync(EVENTS, "utf8").split("\n").filter(Boolean)
      .map((l) => { try { return JSON.parse(l); } catch { return null; } })
      .filter(Boolean);            // one bad line costs one event, not the endpoint
  } catch { return []; }
}

    No rotation, deliberately deferred

    Nothing trims events.jsonl. The README says so plainly — "rotate/trim if it ever gets large (personal scale: fine for a long time)". A conscious trade with a known expiry, not an oversight. It will need a cutoff eventually.

    05 · the money

    Two price tables kept in sync by a comment

    Cost is never stored. Events carry raw token counts and a model id; the dollar figure is computed at read time — in two independent places. The server has its own PRICES table for historical aggregates, and the client has MODELS in lib/routing.ts for live figures as events stream in.

    There is no shared import and no build-time check. The server file's entire safeguard is a comment reading "mirror lib/routing.ts". If one changes and the other doesn't, the historical total and the live total silently disagree, and nothing surfaces it but noticing that two numbers which should match don't.

    The "saved vs all-Opus" figure is a counterfactual, not a measurement: it recomputes what the same tokens would have cost at Opus pricing. That's the routing policy made visible as a real dollar delta per turn.

    Sonnet 5's introductory rate ends 2026-08-31. On 2026-09-01 both the server's PRICES and lib/routing.ts need a manual edit, or every Sonnet turn under-reports and the savings bar overstates. Cache reads are billed at 0.1× input — also replicated by hand in both.

    06 · same project, two paths

    The server has no idea what a project is

    /projects buckets by literal cwd, which is correct and useless. The vault is /Users/thomas/secondBrain from the laptop and /root/secondBrain from the cloud host — different user, different $HOME, same project. The server cannot know that, so it returns two rows for one thing.

    The dashboard merges them client-side by the last path segment, shows the most recently touched host as the primary card, and folds the others into an "also on: cloud · 2h ago" trail. Hiding the other host was explicitly rejected — the point is to see that both machines have been in here.

    The fix lives in the view, not the data

    Any second consumer of /projects — a CLI, a widget — inherits the unmerged, duplicated-by-host view unless it reimplements the same merge.
