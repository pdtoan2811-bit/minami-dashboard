    Minami Bento · pipeline 1 of 3

    Reading someone else's append-only log, cheaply

    Bento doesn't instrument Claude Code. It reads the JSONL transcripts Claude Code was already writing — files that reach 61 MB, change every few seconds while a session is live, and number in the hundreds. Nearly every hard problem in this codebase comes from that one decision, and every fix below was a real stall someone sat through.

    01 · the cold start

    Nine seconds of nothing

    listSessions() needs metadata for every session file before the grid can paint a single tile: tokens, cost, title, last activity. The obvious implementation reads each file and parses every line. With real transcripts at 29–61 MB and hundreds of them on disk, that measured about nine seconds of synchronous work on every cold launch — and because Node runs one event loop, the whole UI sat behind it.

    The fix is a metadata cache keyed by (mtime, size), mirrored to ~/.minami-bento/meta-cache.json. loadDiskCache() hydrates it before anything is parsed, so a cold launch serves known files from cache and reads only what changed. 9.3 s → 8 ms.

    The same Map is also parked on globalThis. That's not belt-and-braces for its own sake: a Next dev hot-reload re-runs module top-level code, which would otherwise discard a warm cache mid-session. Two independent survival paths for the same state — process memory for a hot reload, disk for a hard restart.

    // two survival paths, deliberately
const cache = ((globalThis as any).__minamiMetaCache ||= new Map());
const META_CACHE_FILE = path.join(os.homedir(), ".minami-bento", "meta-cache.json");

    02 · the parser

    Read only what's new

    Caching by modification time solves the cold start and does nothing for the case that hurts most. An active session appends on nearly every turn, so its mtime changes on nearly every poll — and the original summarize() responded by re-reading and re-parsing the entire file. On a 29 MB transcript that meant blocking the event loop every few seconds, for every request and every open pane, for as long as that session stayed live.

    The file is an append log, so treat it as one. readNewBytes(file, readStart, size) reads only the bytes added since last time, and a ParseAccum carries running state across polls instead of being rebuilt. Cost becomes proportional to what changed, not to how much history has piled up.

    The byte that isn't a character

    An arbitrary byte range can end mid-way through a multi-byte UTF-8 character. Buffer#toString doesn't throw — it substitutes U+FFFD, corrupting text that was perfectly valid on disk. splitTrailingIncompleteUtf8() walks back up to three continuation bytes, and if the sequence doesn't fit, holds it as byteLeftoverB64 (base64, so it round-trips through the JSON cache) to prepend to the next read.

    03 · trusting the key

    Same size, different file

    Incremental parsing rests entirely on one assumption: that the bytes between cached.size and size are genuinely new content appended after what was already folded in. mtime and size cannot establish that. A truncate-and-rewrite landing on an equal-or-larger size is indistinguishable from an append.

    Nothing would error. readNewBytes() would take an arbitrary slice of unrelated content, foldLine() would fold it into the accumulator — which is never reset on the incremental path — and that session's totals and title would be permanently, silently wrong.

    So the key carries a third element: a SHA-1 of the first 4 KB. A genuine append can never touch bytes that already existed, so the fingerprint is invariant across appends and changes the instant anything rewrites the start of the file.

    // the line that catches a truncate+rewrite
const headOk = !!cached && (cached.size === 0 ||
  cached.head === headFingerprint(file, Math.min(cached.size, HEAD_FINGERPRINT_BYTES)));
const canIncremental = raw === undefined && !!cached && !!cached.accum
  && cached.size <= size && headOk;

    Curated labels wiped by a torn write

    Both disk caches write to a temp file and rename into place. A crash mid-write — or two Next processes sharing a home directory, which has happened here — leaves JSON that fails to parse. For the meta cache that just forces a fresh parse. For the enrichment cache it was worse: a failed read returns {}, and the next enrich() wrote that empty object back, permanently erasing every hand-curated goal and task label.

    04 · the regression

    The same stall, through a different door

    With a correct incremental parser shipped, the app froze again. Not a parser bug this time — a counting one. The meta cache holds 500 entries. This machine has 375 transcripts and climbing. A sweep that touches every file pushes past the bound partway through, so the LRU evicts entries that the same sweep just created, forcing a full re-parse of files parsed moments earlier. On every poll.

    That is the exact failure mode the incremental parser had already fixed, arriving through cache thrash instead of a busted parser. The fix isn't a bigger cache — it's never calling the expensive function on a file that couldn't matter. A stat-only pass ranks every file by mtime and takes the 150 most recent as candidates before summarize() runs at all.

    mtime is a safe recency proxy precisely because any activity touches it, including an in-progress stream — so a genuinely live session can never fall outside the window. 150 is deliberately generous against the eventual 60 tiles, because candidates get dropped downstream; what matters is that it's a fixed number, so per-sweep work never again scales with how much history is on disk.

    05 · the open pane

    A turn that vanished

    An open chat pane polls its transcript roughly every 2.5 seconds. It doesn't need the whole file — just the end — so readTail() reads the last 1.5 MB and starts at the first newline, which guarantees a clean line boundary.

    Except a tool_result carrying a large embedded base64 image can produce a single JSONL line longer than 1.5 MB. The window then contains no newline at all. The old code fed that unaligned blob forward anyway, JSON.parse failed on every line, and the entire turn disappeared from the UI — no error, no placeholder, no indication anything had been dropped.

    Now a missing newline widens the window fourfold and retries, capped at 12 MB. Past that it returns empty, which the caller reads as "no new turns" — a line bigger than 12 MB isn't worth reading the whole file for.

    // the retry that stops a turn from silently disappearing
const nl = s.indexOf("\n");
if (nl >= 0) return s.slice(nl + 1);
if (window >= TAIL_HARD_CAP || window >= size) return "";  // give up, not guess
window *= 4;  // and read again

    Asymmetric freshness, on purpose

    /api/bento/session/[id] serves meta best-effort from cache and never forces a parse — only turns does real I/O, and only on a miss. That asymmetry is exactly what makes a 2.5-second poll per open pane affordable.

    06 · the label layer

    Naming things costs a subprocess

    Tiles carry a semantic Project › Goal › Task label, produced by shelling out to the local claude CLI on Haiku 4.5. The first version used spawnSync — which froze the entire server, including transcript loads for unrelated panes, for the whole duration of every label call.

    It's now async spawn() in a Promise, bounded by a 90-second timeout and an 8 MB output cap, both of which resolve with whatever was captured rather than hanging. Re-labelling is rationed: a session already labelled is only re-run when it is not active and has grown by more than 30 messages, so a live conversation doesn't burn a Haiku call every few turns.

    The write path has a race that is narrowed rather than closed. enrich() reads the cache, then awaits up to 90 seconds — during which another process could write newer curated labels. Writing the original snapshot back would clobber them, so it re-reads immediately before merging. That shrinks the vulnerable window from the whole Haiku call to a single read-then-write. Without a cross-process lock it cannot be eliminated, and the code says so.

    07 · assembly

    Three layers, three cadences

    A tile is assembled from three independently cached layers polled on three different clocks, and none of them trusts another's freshness. The grid route merges parsed metadata with enrichment labels but never triggers enrichment — spending Haiku tokens is the sole job of a separate explicit POST.

    Local only

    listSessions() returns an empty array on Vercel — there is no ~/.claude/projects on a cloud host. The grid isn't broken there; it has nothing to read. Only /dashboard is remote-safe.
