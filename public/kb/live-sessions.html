    A conversation held open by a generator that never returns

    A live pane isn't a transcript viewer. It's one SDK query() call that stays open for the life of the pane, fed by an async generator and drained over SSE. Almost everything difficult here comes from that call outliving the HTTP request that started it — and from its subprocess being a child of the web server.

    01 · the shape

    One query, forever

    Every pane that goes live gets exactly one query() — created once in ensureSession() and held in a registry for the life of the pane. Not one per message. The prompt isn't a string; it's inputGen(s), an async generator that yields queued messages and then parks on an unresolved promise until the next send wakes it.

    That's the whole trick. Streaming-input mode turns a normally one-shot CLI invocation into something you can keep talking to, because the subprocess and its context never tear down between turns.

    // the entire "hold it open" mechanism
async function* inputGen(s) {
  while (!s.closed) {
    if (s.queue.length) { yield s.queue.shift(); continue; }
    await new Promise((resolve) => { s.waiter = resolve; });  // park until sendMessage() wakes us
  }
}

    The registry lives on globalThis so a Next dev hot-reload — which wipes module-level state on every save — doesn't orphan a running subprocess.

    cold.start.sequence

    The race is real, and handled

    The browser fires the POST and opens the EventSource in the same tick, so either can win. A subscriber that arrives first is parked in a separate waiting map and adopted the instant the session is created — otherwise the opening init and activity events stream into the void.

    02 · the wire

    Fourteen event shapes, one stream

    AgentEvent is a fourteen-variant tagged union, and the stream route does nothing but stringify whatever subscribe() hands it. There is no endpoint per event type: the entire live experience is one text/event-stream per pane, plus a handful of POSTs that mutate server state and let the stream report the consequence.

    A 20-second : ping comment line keeps the connection alive through idle-timing proxies. SSE comment lines never fire onmessage, so the client never sees it.

    t: init · delta · thinking · snapshot · detached · tool · tool_end
   activity · notice · permission · ask · result · busy · error
// notice.kind: retry · compact · task · limit · denied · aborted · restarting

    No backpressure

    broadcast() has no flow control, and a subscriber callback that throws is swallowed. A dead client is silently dropped rather than erroring the session — deliberate, but it means a slow consumer can't push back.

    03 · the label

    The server decides what it's doing

    "Reading package.json", "waiting on approval · run: npm test", "compacting 42k → 18k" — none of that is inferred in the browser. It's an eight-state machine tracked per session and rebroadcast with REPLACE semantics on every transition.

    It lives server-side for one reason: the label has to survive a refresh. Every subscribe() replay carries a snapshot with the current activity, so a pane that reconnects mid-tool-call resumes with the real label and a correctly offset clock instead of a generic spinner. And because the whole state is rebuilt every time, a client that misses an event self-heals on the next one rather than accumulating drift.

    activity.phase 
    // the stale-label fix: re-derive from what is ACTUALLY still in flight
function settle(s) {
  if (s.pending.size) return touch(s, "awaiting");              // a human is blocking
  if (s.liveTools.size || s.liveTasks.size) return touch(s, "tool");
  touch(s, s.busy ? "thinking" : "idle");
}

    Without settle(), a finished tool's label stays on screen — run: npm test still animating long after the command exited.

    04 · the pause

    A promise only a different request can resolve

    When Claude reaches for a tool the config doesn't auto-approve, the SDK calls canUseTool() and awaits whatever comes back. Our implementation decides nothing: it broadcasts a prompt, stores {resolve, toolName, input} in s.pending, and returns a promise that only a separate HTTP request can settle. The SDK's entire turn parks there for as long as the human takes.

    That gap is where three separate failure modes live, and each one is defended individually.

    05 · coming back

    Three copies of the truth, one winner

    On reconnect there are three versions of the current turn: the JSONL on disk, the server's in-memory partial, and whatever the browser already painted. Picking wrong either loses text that arrived during the outage, or visibly un-streams text the user already watched appear.

    The deciding signal isn't a guess about which source is fresher — it's timing. Did a token land after the resync started? If not, the local copy is stale-after-an-outage and the server wins. If one did, the connection was live the whole time and the local turn is actually ahead of disk, which hasn't been flushed yet.

    // the arbitration, in one line
const staleAfterOutage = !liveTurn || lastDeltaAtRef.current <= resyncStartedAt;
return [...seed, ...(liveTurn && !staleAfterOutage ? [liveTurn] : overlay)];

    step 1 / 5

    The reap that started a blank session

    Re-attaching used to optimistically mark the pane as backed by a live session. Combined with the idle reaper, that meant the next message could silently start a brand-new, context-less session — the client believed something was there that wasn't. Now that flag is only set by a snapshot (proof it exists) and cleared by detached (proof it doesn't). The reaper also moved from 10 minutes to 30, because backgrounding a mobile tab tears down SSE routinely and shouldn't cost you a warm subprocess.

    06 · the deploy problem

    Redeploying kills every conversation on the box

    Every live session's subprocess is a child of the Next server process. The deploy step kills whatever holds port 3000 — so it doesn't just swap the UI, it takes down every in-flight turn on the machine, along with their MCP servers.

    The cruel part is who it lands on. The trigger is usually a different pane finishing an edit and redeploying, so the interruption arrives at whoever happens to be typing. That's the real source of "my request got interrupted and I never touched anything."

    The mitigation is a drain, and it is honestly labelled as one. Before the kill, drainForRestart() broadcasts a restarting notice to every open pane — the one notice a user gets before the disruption rather than after — then polls until no session is busy, up to a timeout. Turns that land inside that window write their result to the JSONL, which is exactly what a pane reconciles against when it reattaches to the new build.

    // deliberately closes nothing — the caller is about to kill the process anyway
while (Date.now() - startedAt < timeoutMs) {
  const busy = eachSession().filter((s) => s.busy).length;
  if (!busy) return { drained: true, stillBusy: 0, waitedMs: Date.now() - startedAt };
  await new Promise((r) => setTimeout(r, 250));   // poll, don't hook every completion path
}

    A blast-radius reducer, not a fix

    The durable fix is hosting sessions outside the process that gets redeployed. The code says so itself. Until then a deploy can still cut a turn off — the drain only makes it rarer, announced, and recoverable from the transcript.

    Why the drain endpoint needs a token

    The obvious gate — "only allow loopback" — cannot be built here. A Next route handler has no access to the peer socket address, and x-forwarded-for proves nothing: Next backfills it from socket.remoteAddress, so its presence isn't evidence of a proxy hop, and it only fills the header when absent — so any LAN client can send x-forwarded-for: 127.0.0.1 with curl -H and have it preserved verbatim. An early version treated presence as proof and 403'd its own loopback caller.

    So it gates on a shared secret in a 0600 file instead, compared with timingSafeEqual after a length precheck (that function throws on mismatched lengths, which would leak length through the error path). No token file means deny — it fails closed.

    07 · two keys

    One session, registered twice

    Once the SDK reports a real session id, the same Session object is stored under a second key: live:<sessionId> alongside its pane key. That's load-bearing — it's what lets any tab open a running session by its real id rather than only the tab that started it.

    It also means any code that walks the registry naively visits every live session twice. Three call sites dedupe by object identity; the health endpoint's comment spells out the consequence of forgetting — it would report twice the real load, and a deploy script would think a restart kills twice as many chats as it does.

    function eachSession() {
  const seen = new Set();
  for (const s of store.values()) {
    if (seen.has(s) || s.closed) continue;   // identity dedup across both keys
    seen.add(s); out.push(s);
  }
}

    Teardown has the mirror of this problem: it must remove both aliases, and only if they still point at this object — a late cleanup must not delete the registry entry of a successor that reclaimed the same pane key.

    Discipline, not structure

    Nothing in the type system stops a fourth call site from walking the registry and forgetting to dedupe. It's a convention held by comments.
