    Minami Bento · running it

    Deploying a thing that is running your work

    This app hosts live Claude sessions inside its own web server, so a deploy is not a neutral act — it ends conversations. Add an account switcher that lies about which account is active, and "operations" stops being routine. Here's what to do, and what to check when something is wrong.

    01 · shipping

    Production mode, on purpose

    bin/serve.sh builds and swaps a production server. That's not a performance choice — it's because you edit this app from inside this app. Dev mode's Fast Refresh hot-patches the running page, which changes React's hook signatures mid-session and crashes the very tab you're working in. Production has no Fast Refresh, so a rebuild cannot touch the tab driving it.

    The swap kills only the process bound to the port, so a separate iteration server on :3001 survives untouched.

    bash bin/serve.sh            # refuses to swap while a turn is in flight
bash bin/serve.sh --force    # swap anyway — still warns the panes first

    The refusal is the important part. Because sessions are children of the server, a deploy ends every conversation on the box — and the trigger is usually a different pane finishing an edit, so it lands on whoever happens to be mid-sentence.

    step 1 / 5

    The check must happen before the build

    The build is the point of no return — it replaces .next underneath the server currently reading it. Bailing out after that would leave the old process serving a build it no longer has on disk, so the "is anyone busy?" veto runs first, while backing out is free.

    02 · whose account

    The status banner is a label, not evidence

    Claude Max accounts are pooled and swapped by a separate CLI. When the active credential dies it silently fails over to whichever slot is ready, and nothing says so — you keep working, and hours land on the wrong weekly limit.

    The obvious fix is to read the CLI's own status. That fix is wrong. Its active field only echoes a label written on the last switch attempt; it is not proof the switch took. This was verified the hard way.

    // 2026-07-29 — these disagreed, and the CLI was the one lying
state.json      active_slot = oedevai2@gmail.com      ← a label
~/.claude.json  oauthAccount.emailAddress = pdtoan2811@gmail.com   ← the truth

    So the alert reads ~/.claude.json, which Claude Code writes from the credential it actually authenticated with. It also reports when the CLI's claim disagrees with reality — because that means "switch back" may report success and change nothing, which is why the alert re-verifies after switching rather than trusting the output.

    QuestionDo not askAsk
    Which account am I on?tok status's banner~/.claude.json → oauthAccount.emailAddress
    Did the switch work?the command's exit codere-read the identity afterwards
    Is this account healthy?that it's currently livewhether the slot has a full capture — nulls mean it can't self-refresh

    A live account can still be primed to die

    A pooled slot can be a degraded capture — oauth_account, plan and refresh_token_expires_at all null — even while that account is working. The CLI then can't proactively refresh it, so the silent expiry recurs. Being logged in now is not evidence it's fixed.

    03 · reading the docs

    The knowledge base outlives the app

    Everything you're reading serves itself. That matters because bin/serve.sh takes :3000 down on every deploy and refuses to restart mid-turn — so the documentation would be unreachable exactly when something is broken, which is when you want it.

    npm run kb                      # → http://localhost:4400
open "Open Knowledge Base.command"   # double-click from Finder

    Zero dependencies, resolves its own root, walks the port up if it's taken. It uses KB_PORT and refuses to start if that equals the app's port — because PORT is already spoken for here, and reading it once bound the KB server to 127.0.0.1:3000 alongside the dashboard's IPv6 wildcard. macOS permits that pairing instead of raising an error, so requests split between two servers at random.

    04 · when it's wrong

    What to check, in order

    Most confusion here comes from a signal that looks authoritative but is only a claim. The runbook is mostly "go find the thing that cannot lie."

    SymptomMost likelyCheck
    A turn died and nobody touched it another pane deployed the pane gets a restarting notice first — look for it before assuming a bug
    "OAuth session expired" a pooled account lapsed ~/.claude.json for the real identity; switch to the healthy slot, then restart the worker
    Deploy "succeeded", nothing changed the swap never ran the build exiting 0 is not evidence — curl the route and confirm
    The grid is empty running somewhere without ~/.claude the home page is local-only by design; only /dashboard is remote-safe
    Every pane frozen at once the event loop is blocked transcript parsing — see the transcript pipeline
    Dashboard shows no usage the collector died or the hook is silent systemctl status minami-metrics; the hook fails silent by design, so absence of data is its normal failure mode
    A dialog with no working button the session ended holding the prompt should self-heal — every terminal path auto-denies; if not, reload the pane

    The pattern behind almost all of it

    An mtime. A status label. A reported success. A reopened socket. A build that exited 0. Each looked like evidence and was only a claim. When something here is inexplicable, the useful question is "what am I trusting that hasn't actually been verified?"
