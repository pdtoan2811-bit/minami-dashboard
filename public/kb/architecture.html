    Minami Bento · architecture

    Every Claude Code session on your machine, as a live tile

    Minami Bento reads transcripts Claude Code was already writing, drives new sessions through the Agent SDK, and folds in usage from a second machine — three independent pipelines that meet in one browser tab. This is what each one does, and why the non-obvious parts are shaped the way they are.

    01 · the map

    Three pipelines, one tab

    Nothing here is a single flow. Three separate pipelines run at once, and most confusion about the codebase comes from reading one and assuming it explains another.

    The live drive (top row) is the one that feels like a chat: your browser posts a message, a server-side registry hands it to the Agent SDK, and the SDK spawns the real claude CLI. The read-back (middle row, flowing right to left) is what fills the grid: that same CLI appends to a JSONL transcript on disk, and a parser turns those files into tiles. The two meet in your browser but never talk to each other directly — disk is the only thing they share. The metrics pipeline (bottom) is fully independent and runs on every machine you use, not just this one.

    browser live session disk parse & cache metrics

    The boundary that decides everything

    The grid and the live panes both need ~/.claude/projects and a local claude login. That makes the home page local-only — deployed to Vercel it renders, but finds zero sessions. Only /dashboard is remote-safe, because it reads a network API instead of a home directory.

    02 · the substrate

    The data was already there

    Bento does not instrument Claude Code. It reads what Claude Code already writes: one append-only JSONL file per session, under a directory named after the working directory with slashes turned into dashes.

    ~/.claude/projects/-Users-thomas-minami-dashboard/
  cd27fae5-2d99-4ad0-bd16-e23f9f0d3e7c.jsonl   ← one session
  4f1a....jsonl
  ...375 more on this machine, some 29–61 MB

    The slug is the absolute cwd with / → -. That is also why memory never transfers between machines: a different home directory is a different slug.

    This choice is the reason the whole product is possible in a weekend, and also the reason for every hard problem in the next three sections. Reading someone else's append-only log is cheap the first time and expensive if you keep re-reading it.

    listSessions.pipeline

    Why stat first

    fs.statSync on 375 files costs microseconds. Opening them costs seconds. The candidate window exists so summarize() is never called on a file that couldn't possibly be relevant — filtering before the expensive step, not inside it.

    03 · the parser

    Read only what's new

    The first version of the parser read the whole file whenever its modification time changed. That sounds harmless until you notice what an active session does: it appends on nearly every turn, so its mtime changes on nearly every 5-second poll. On a 29 MB transcript, that meant re-reading and re-parsing 29 MB every few seconds — on Node's single event loop, which every other request and every open pane was also waiting on.

    The fix is to treat the file as what it is: an append log. Keep a running fold state per file, and on each poll read only the bytes past where you stopped.

    incremental.read
    step 1 / 4

    The cache key is not just the modification time. It is (mtime, size) plus a SHA-1 of the first 4 KB. That third element exists for one specific failure: a file that gets truncated and rewritten to a coincidentally equal-or-larger size. Under mtime-and-size alone that is indistinguishable from an append, so the parser would fold entirely unrelated bytes into the accumulator and produce a permanently wrong total with no error anywhere.

    The byte that isn't a character

    Reading an arbitrary byte range can land mid-way through a multi-byte UTF-8 character. Buffer#toString quietly replaces the fragment with U+FFFD — corrupting a line that was perfectly valid on disk. splitTrailingIncompleteUtf8() holds the trailing fragment back and prepends it to the next read.

    04 · the caches

    Three caches, three different bounds

    Every cache here is bounded, and each bound was chosen for a different reason. An unbounded Map keyed by session id is a real leak — one entry per session ever seen, growing for the life of the process.

    CacheBoundKeyed byWhy this bound
    meta cache
    ~/.minami-bento/meta-cache.json    		 500mtime · size · head SHA-1 Mirrored to disk so a cold launch reads the cache instead of re-parsing every file — the measured difference was 9.3 s → 8 ms.
    turns cache60file mtime Holds parsed turns for an open pane. Small because only a few panes are ever open.
    id → path index2000session id Pure lookup table, cheap per entry, so it can afford to be large.
    candidate window150mtime rank Not a cache — a pre-filter. See the trap below.

    Cache thrash: the bug that hid inside the fix

    With 375 transcripts and a 500-entry cache, summarizing every file on every sweep pushes past the bound mid-sweep — so the sweep evicts and force-reparses large files that the same sweep just cached. The event loop blocks again, with a perfectly correct parser and a perfectly correct cache. Capping candidates to the 150 most recent is what actually closed it.

    Both disk-mirrored caches write to a temp file and rename into place. A torn write leaves JSON that fails to parse, which returns {} — and for the enrichment cache the next write would then persist that empty object, permanently erasing every hand-curated label.

    05 · the live turn

    One message, end to end

    A live pane is not a transcript viewer. It holds a long-lived query() from the Agent SDK in streaming-input mode, so the same session takes message after message — exactly like the CLI. The browser and that session communicate over two channels at once: a POST to send, and an EventSource to receive.

    turn.sequence

    Two keys, one session

    Every session sits in the registry under two keys: the pane that started it, and — once the SDK reports its real id — live:<sessionId>. That second key is what lets a different pane, or the same pane after a refresh, find a session that is already running instead of starting a cold duplicate.

    // manager.ts — the registry lives on globalThis so a dev hot-reload
// doesn't orphan running sessions and leak their subprocesses.
const store = ((globalThis as any).__minamiAgentStore ||= new Map());
store.set(key, s);                    // pane-1785…-3-a7f
store.set(SID_KEY + m.session_id, s);  // live:cd27fae5-…

    Both keys, or a leak

    Anything that removes a session has to remove both aliases, and identity-check (store.get(s.key) === s) before deleting — otherwise cleanup for a dead session can delete a newer one that has since claimed the same pane key.

    06 · the label

    Saying what it's doing, honestly

    "Working…" is a useless label. The server tracks a real phase per session and derives a specific line — reading package.json, waiting on approval · run: npm test — from what is actually in flight.

    This is computed server-side on purpose. It survives a browser refresh by riding the reconnect snapshot, and it makes it impossible for the inline transcript indicator and the composer status line to disagree, because there is only one source.

    activity.phase

    Two details do most of the work. Tool labels refine while the arguments are still streaming — partial JSON is parsed on each delta, so a fast tool shows its real target for essentially its whole life instead of flashing a generic placeholder. And settle() recomputes the phase from what remains in flight after a tool result lands, rather than leaving the finished tool's label on screen.

    // the stale-label bug: without settle(), a finished tool keeps animating
function settle(s) {
  if (s.pending.size) return touch(s, "awaiting");        // a human is blocking
  if (s.liveTools.size || s.liveTasks.size) return touch(s, "tool");
  touch(s, s.busy ? "thinking" : "idle");
}

    07 · the dropped connection

    Surviving a refresh, and a tunnel

    This is a mobile-first dashboard, so connections drop constantly — switching networks, a laptop sleeping, a proxy killing an idle stream. EventSource reconnects at the transport level silently, which is the problem: the socket comes back, but everything that streamed during the gap is simply missing, and nothing above the transport knows.

    The fix is to notice. Any onopen past the first is treated as a reconnect: tear the stream down and reopen it as an explicit re-attach, which is the same path a manual refresh takes. The server answers a re-attach with a snapshot — in-flight text, busy state, live activity, and any permission prompt still waiting on an answer.

    Which copy is right?

    After a resync you hold two versions of the turn: what the browser has, and what the server just sent. Prefer local blindly and you lose everything that arrived during the outage. Prefer the server blindly and you roll back text the user already watched appear. The tiebreak is timing — did a delta land after the resync started? — not a guess about which source is fresher.

    The same "don't trust it, verify" instinct shows up in the permission lifecycle. A prompt is a promise parked in a map, and a promise nobody resolves pins the session busy forever — no result will ever arrive to trigger cleanup, so the session and its subprocess leak permanently. Three separate paths therefore auto-deny an orphaned prompt: the idle reaper, the consumer loop's finally, and closeSession().

    08 · the second machine

    Two machines, one number

    Work happens on the laptop and on a Hetzner box that runs the Minami bot. Counting usage on only one of them is worse than not counting: it looks precise and is wrong.

    The collector is deliberately boring — a zero-dependency Node server appending one JSON line per turn. It binds to loopback only and is published through a Tailscale Funnel, which gives real HTTPS on a *.ts.net name with no domain to buy and no inbound port to open.

    The read key is obscurity, not auth

    INGEST_TOKEN genuinely gates writes. READ_KEY travels as NEXT_PUBLIC_*, which means it is compiled into the browser bundle and visible to anyone who loads the page. Real privacy has to come from gating the deploy itself.

    09 · whose account is this

    Don't trust the banner

    Claude Max accounts are pooled and swapped by a separate CLI, token-slayer. When the active account's credential dies, it silently fails over to whichever slot is ready — and nothing anywhere says so. You keep working, and hours of usage land on the wrong weekly limit.

    The obvious implementation is to read the CLI's own status output. That implementation is wrong. Its active field only echoes a label written on the last switch attempt; it is not evidence the switch took.

    // verified 2026-07-29: these two disagreed, and the CLI was the liar
state.json      active_slot = preferred@example.com     ← a label
~/.claude.json  oauthAccount.emailAddress = other@example.com  ← the truth

    Claude Code writes oauthAccount from the credential it actually authenticated with, so it cannot drift the same way.

    So /api/accounts layers a live block on top of the CLI output, read from that file, and the alert triggers on that. It also reports claimsMismatch — the CLI disagreeing with reality is itself worth surfacing, because it means a "switch back" may report success without changing anything. Which is why the alert re-reads identity after switching rather than believing the output.

    10 · the scar tissue

    What broke, and what fixed it

    Most of the non-obvious code in this repo is not cleverness. It is a specific incident that happened once. Kept together, the list is the honest shape of the project.

    What brokeWhyThe fix
    Every pane froze while one session streamed Full re-read + re-parse of a 29 MB transcript on every mtime change, blocking the event loop Incremental fold over appended bytes only
    It froze again, with a correct parser 375 files vs a 500-entry cache — each sweep evicted what it had just cached Stat-only pre-filter to the 150 most recent
    Curated labels vanished Torn cache write → unparsable JSON → {} → written back as empty Atomic temp-file + rename, re-read before merge
    The whole server died An un-awaited SDK promise rejected with no handler; Node's default is to exit Process-level handlers in instrumentation.ts
    The metrics collector died JSON.parse("null") doesn't throw — the next line did Null-check plus the same process-level net
    A dialog with no working button Session ended holding an unresolved permission promise Auto-deny on every terminal path
    Stop denied the wrong turn A fast follow-up's prompt landed in pending mid-interrupt() Snapshot pending entries before awaiting
    Silently billing the wrong account Trusting a CLI's own status label as evidence Read the credential Claude Code actually used

    The pattern

    Six of these eight are the same mistake in different clothes: trusting a signal that looks authoritative but is only a claim — an mtime, a status label, a reported success, a connection that reopened. The recurring fix is to find the thing that cannot lie and check that instead.
